ROS–CM530 雙手臂直接轉接規格書
============================================================
適用專案：16 CM530 DUAL ARM
主機序列協定：4
馬達通訊：Dynamixel Protocol 1.0（不是主機協定版本號）
更新日期：2026-09-30
依據：已核准的直接轉接需求與第 16 版實作
讀者：ROS 中控、運動規劃、序列轉接及整合測試開發者

「必須」表示本系統對 ROS 端的對接要求；「韌體行為」描述已實作內容。
本儲存庫不提供 ROS 節點、topic/service/action 定義或 micro-ROS 移植。
ROS 發行版與內部訊息介面可由系統端選定，但序列邊界必須符合本規格。
通訊範例的 512／520 只是資料範例，不是實機校正或工作區座標。

1. 系統責任與資料流
------------------------------------------------------------

資料流：
環境相機／兩臂手眼相機 -> 視覺與校正 -> ROS 任務協調／運動規劃
ROS 算出的四軸原始目標 -> 序列管理者 -> CM530 -> 指定手臂的 AX-12A
ROS 通知的動作／停止顯示 -> 同一序列管理者 -> CM530 -> 板上左右 LED
CM530 -> ACK／ERR -> 序列管理者 -> ROS 命令傳送結果
ROS -> 另外的 ESP32 控制介面 -> 吸盤／電磁閥

ROS 必須負責：
- 視覺、3D 座標、座標系轉換、手眼校正與定位可信度。
- IK、角度／rad 到 position 的換算、關節方向、零位、機械限制。
- 目標姿態、路徑、插值、軌跡點列、取樣與發送時間。
- Idle/Pick/Place/Return 狀態機、B 站鎖、C 站格位與搬運順序。
- 吸取／放置成功、實際到位、離開共享區的判定與異常恢復。
- 監控、記錄、命令來源管理與安全策略。

CM530 僅負責：
- 解析命令、檢查格式／數值、辨識 arm1 或 arm2。
- 固定四顆馬達的 Goal Position 或 Torque Enable SYNC_WRITE。
- 開機 torque-off、初始化失敗鎖定、每臂有效目標資格。
- 依 ROS LED 命令切換左右兩臂紅綠燈；不自行推算動作狀態。
- 回覆本地處理／傳送結果及 UART 損壞行恢復。

CM530 不接收影像、XYZ、rad、degree、速度、dt_ms、軌跡 ID、seq、
A/B/C 區域、格位編號、任務狀態或吸盤命令；不發送 READ。
ROS 不得把韌體「有效目標」推論成馬達已到位或 torque 已啟用。


2. A／B／C 任務與 ROS 協調要求
------------------------------------------------------------

2.1 相機責任
環境相機由上往下觀測桌面，判斷 A／B 站物品狀態及全域場景。
兩臂手眼相機提供物品 3D 座標、抓取前定位與放置前再確認；
C 站格位占用由手眼視覺判斷。影像辨識品質不由韌體判斷。

2.2 四狀態任務機
手臂 1：
  0 Idle：等待 A 站有可取物品。
  1 Pick A：定位、規劃並前往 A 站，透過外部吸盤介面取物。
  2 Place B：取得 B 站鎖並確認可放置，再前往放物。
  3 Return：返回 ROS 定義的待機姿態；依完成條件轉回 Idle。

手臂 2：
  0 Idle：等待 B 站有可取物品且 C 站有可用格位。
  1 Pick B：取得 B 站鎖、定位並取物。
  2 Place C：前往選定的 C 站空格，放置並確認。
  3 Return：返回 ROS 定義的待機姿態；依完成條件轉回 Idle。

這些狀態不是序列命令。每個移動步驟都由 ROS 產生 AX 目標序列。
Return 姿態必須來自 ROS 的機構配置；不得固定以四軸 512 當已校正姿態。
ACK 只更新「命令傳送結果」，不能直接觸發實體步驟完成。

2.3 B 站共享資源
- ROS 維護唯一 B 站鎖持有者，兩臂不得同時取得。
- 取得鎖與允許進入必須是同一個協調器的一致決策，避免兩臂各看對方狀態後同時進入。
- 手臂 1 放物及手臂 2 取物，都必須在進入共享區前取得使用權。
- 釋放鎖必須依據實際離開共享區的完成判斷，不能依賴 AX 的 OK。
- 通訊故障、重啟或位置不明時，不可自動宣告共享區空閒。
- CM530 不知道 B 站，也不會替 ROS 拒絕造成區域衝突的合法 AX。

2.4 C 站八格
- 格位固定為 2 × 4，共 1～8 號；格號在實際桌面的方向與座標由 ROS 校正配置。
- ROS 維護占用、預留與無法確認的格位資訊，避免把已預留或未知格位當作可用。
- 每次放置前依手眼視覺確認格位，從可用空格中選編號最小者並預留。
- 若 1～4 號已占用、5～8 號可用，則選 5 號；再由 ROS 計算放置姿態。
- 放置後依外部確認更新占用；失敗或資訊過期時不得把該格記為成功完成。
- 八格全部確認占用後回報 C 站排列完成，不再建立新的 C 站放置任務。
- 暫時全部被預留或看不清楚，不等於八格已滿。
- 本版不做形狀分類；不把格位、占用或完成訊息發給 CM530。

系統全流程完成、回待機與後續補料的策略由 ROS 協調器管理。


3. 硬體與關節資料
------------------------------------------------------------

一塊 CM530、一個主機序列埠、共用 TTL bus、兩臂各四軸。
沿用由下到上的 j1/j2/j3/j4 順序：
  arm1 = [17, 3, 2, 15]
  arm2 = [12, 1, 8, 16]

主機通訊：USART3，57600 baud，8N1，無 RTS/CTS 或 XON/XOFF。
馬達通訊：USART1，1 Mbps，Dynamixel Protocol 1.0。
位置單位：AX-12A 原始整數 0～1023，每筆固定四軸。
Torque Enable：0 或 1，整支指定手臂四軸使用相同值。

韌體不修改馬達 ID、EEPROM、既有速度、限位或零位。
ROS 發送前必須做每個關節的機構限制與路徑檢查。
四軸都在 0～1023 不代表機械姿態或路徑可行。

馬達封包：
- AX：Broadcast ID 254、SYNC_WRITE、位址 30、每軸 2 bytes、小端序。
  只含指定手臂四個 ID；封包共 20 bytes。
- TORQUE：Broadcast ID 254、SYNC_WRITE、位址 24、每軸 1 byte。
  只含指定手臂四個 ID；封包共 16 bytes。
- 依 Protocol 1.0 SDK 產生 checksum。廣播寫入不逐顆確認馬達回覆。
- AX／TORQUE 都不包含另一臂 ID，不包含速度或其他暫存器更新。
- PING/VERSION 為 CM530 本地診斷，不是馬達 PING。
- LED 只更新板上 GPIO，沒有馬達封包。


4. 序列格式與解析規則
------------------------------------------------------------

正式傳輸：
  ASCII，大寫命令、小寫 arm1/arm2、半形逗號、十進位整數、LF 結尾。
  例：AX,arm1,500,501,502,503\n

韌體接受 LF、CR、CRLF；回覆以 CRLF 結尾。
接收端必須組合完整行，不能假設一次 read() 就是一行。
空行／僅空格或 tab 的行不回覆，不應拿來當探測命令。

相容輸入：
- 命令與手臂大小寫不拘；各欄位兩側空格/tab 可忽略。
- 行首 UTF-8 BOM 與 UTF-8 全形逗號可正規化；ROS 不應依賴這項人工輸入相容功能。
- AX/TORQUE 的整數可帶 + 或 -，有前置零亦可；先檢查 signed 32-bit，再檢查命令值域。
- 不接受小數、指數、十六進位、數字內空白或數字後附雜訊。
- NUL 不會截斷指令使後段被隱藏，會造成非法內容而被拒絕。
- backspace/delete 可刪除尚未完成行的最後一個 byte，僅供手動輸入。

行緩衝區 96 bytes，最多 95 bytes 原始內容（不含行尾）。
超限／UART 丟資料：回 ERR,OVERFLOW，丟棄到下一個 CR 或 LF；
同一損壞行不重複報錯，也不執行尾端殘留命令。
ROS 收到 OVERFLOW 後仍必須停止整個連線的後續動作發送，不自動續送。

正常非空且沒有資料丟失的命令，一行對應一行結果。
協定沒有主機行 checksum、request ID、timestamp、軌跡序號或去重機制。


5. 開機、版本與連線生命週期
------------------------------------------------------------

5.1 板子開機
應用程式配置 LED GPIO，將兩臂設為紅色待命，再清除目標資格並依序送 arm1/arm2 torque-off。
開機紅燈是預設待命顯示，不代表感測到停止；bootloader 階段燈號不在此保證內。
即使第一筆失敗仍嘗試第二筆；不送位置命令。
兩筆都本地傳送成功：
  READY,4
任一失敗：
  ERR,INIT_FAILED
之後 AX/TORQUE 鎖定，只有板子重新啟動才能重新初始化。
PING/VERSION/LED 仍可用，但不證明馬達初始化成功；LED 不解除動作鎖定。

READY,4 只代表本地初始化封包已傳送，不證明馬達真的關 torque。
重新連線不等於重啟，不能把開埠當成 torque-off。

5.2 主機握手
1. 獨占開啟序列埠，禁止業務動作發送。
2. 監聽 READY,4，終端預設最多 6 秒。
3. 無論是否看見 READY，都送 VERSION，要求完整且精確的 VERSION,4。
4. 送 PING，要求 PONG。
5. ROS 依自己的重新連線／硬體恢復策略決定是否允許新動作。

READY 可能在主機開埠前已發出，因此允許缺席，但 VERSION 不可省略。
READY、READY,2/3、VERSION,2/3 或其他版本均不相容，不得靜默降級。
啟動監聽收到 ERR 或非預期資料就停止；不得忽略錯誤後繼續 demo。
即使 VERSION,4 成功，也不能據此確認 torque 狀態或恢復舊點列。

5.3 運行中異常
主機每次只保留一筆待回覆命令。每筆命令送完後回覆期限預設 2 秒。
收到任何 ERR、錯配回覆、部分行超時、無回覆、序列錯誤或 READY：
- 停止該連線後續動作；停止兩臂共用發送佇列。
- 回報本筆命令、原始回覆／原因及連線狀態。
- 不自動重送、不補送 TORQUE,0 或 LED、不接續舊軌跡。
- 通訊失敗可能發生在動作已傳送之後，必須標示物理結果未知。
- 明確恢復由上層決策；重新握手後建立新計畫，不沿用舊 pending ACK。

已送出的目標可能繼續執行。停止主機發送不等於機械停止。
板子沒有通訊中斷 watchdog 動作，也不會自動卸力。


6. 命令詳細契約
------------------------------------------------------------

6.1 PING
請求：PING
成功：PONG
沒有參數，不發馬達封包，初始化失敗時仍可用。

6.2 VERSION
請求：VERSION
成功：VERSION,4
沒有參數，不發馬達封包；僅辨識主機協定版本，不是 readiness/status 查詢。

6.3 AX
請求：AX,<arm>,<j1>,<j2>,<j3>,<j4>
成功：OK,AX,<arm>
arm 為 arm1 或 arm2；j1～j4 各為 0～1023。
必須先完整驗證四個值，才送一筆四軸目標 SYNC_WRITE。
本地傳送成功後建立該臂目標資格，失敗回 ERR,DXL_TX,<arm> 並清除資格。
不啟用 torque、不等待到位、不記錄或檢查軌跡順序。
重複發送相同 AX 仍會再次寫入；不去重，也不自動重試。
格式或範圍錯誤不送封包，也不清除原有資格。

6.4 TORQUE
請求：TORQUE,<arm>,<enabled>
成功：OK,TORQUE,<arm>,<enabled>
enabled 只能是 0 或 1。
0：在傳送前清除該臂資格，再送四軸 torque-off；失敗也保持資格清除。
1：若無有效目標，回 ERR,NO_TARGET,<arm> 且不傳送；否則送四軸 torque-on。
本地傳送失敗回 ERR,DXL_TX,<arm>。
TORQUE,1 成功或失敗均不改變目標資格；主機遇 ERR 仍停止連線操作。
ACK 中 enabled 以 0／1 正規化，必須與請求完全對應。

6.5 已移除／不支援
HOME、HOLD、BEGIN、PT、END、STOP 不再執行，正常舊格式回 BAD_CMD。
單值 AX,<arm>,512 回 BAD_ARG。
ALL/BOTH、八軸命令、Read/GET_POSITION、速度控制／馬達狀態查詢／吸盤命令皆不提供。
不得把已移除命令靜默轉譯或聲稱韌體會替 ROS 執行其行為。


6.6 LED：每臂顯示狀態
請求：LED,<arm>,MOVING 或 LED,<arm>,STOPPED
成功：OK,LED,<arm>,MOVING 或 OK,LED,<arm>,STOPPED
arm 僅接受 arm1/arm2。命令、手臂及狀態輸入大小寫不拘；回覆固定大寫狀態。
欄位數、手臂或狀態錯誤回 BAD_ARG，不改燈；重複狀態正常 ACK。

映射（顏色由使用者確認，腳位參考 01 LED）：
  arm1 左欄：MOVING = MANAGE PB13 綠；STOPPED = PROGRAM PB14 紅。
  arm2 右欄：MOVING = TX PC14 綠；STOPPED = RX PC15 紅。
  PLAY PB15、AUX PB12 熄滅；POWER PC13 不變。
  TX/RX 已改為 arm2 顯示，不作通訊活動閃燈。

GPIO 低電位亮、高電位滅；同臂先滅舊燈再亮新燈，每臂只亮一個顏色。
不影響另一臂、不送馬達封包、不改目標資格、不啟停 torque。
馬達初始化失敗時仍接受合法 LED，AX/TORQUE 仍被 INIT_FAILED 鎖定。
LED ACK 只表示 GPIO 設定已執行，不確認 LED 元件、物理動作或停止。

STOPPED 是顯示參數，不是停止馬達命令；舊 STOP 不支援。
只有 LED 命令與韌體重新初始化會改燈；AX/TORQUE 成功或失敗皆不改燈。
退出、demo 完成、通訊斷線或錯誤都不自動追加 LED。
重啟回雙紅；其他情況保留最後主機通知，因此斷線可能保留舊顯示。


7. 每臂目標資格與失敗效果
------------------------------------------------------------

韌體每臂僅有 targetValid 這個軟體資格，兩臂互不影響。
它表示：最近一次符合條件的目標封包已由本地傳送路徑送出，
不是馬達存在、保存了正確目標、已到位或 torque 狀態的證明。

事件                                 targetValid
開機                                 false
合法 AX 傳送成功                      true
合法 AX 傳送失敗                      false
合法 TORQUE,0 開始（成功或失敗）      false
TORQUE,1（成功／失敗／NO_TARGET）     不改變
非法參數／範圍／未知命令              不改變
另一臂的合法／失敗命令                不改變
LED 命令（合法或錯誤）                 不改變

初始化失敗則另有全域動作鎖定，資格不能繞過它。
韌體不保存軌跡 active、trajId、expected、received 或最後位置的替代值。


8. 回覆與錯誤碼
------------------------------------------------------------

成功格式：
  PONG
  VERSION,4
  OK,AX,<arm>
  OK,TORQUE,<arm>,0|1
  OK,LED,<arm>,MOVING|STOPPED

事件：
  READY,4              只在成功啟動時輸出
  ERR,INIT_FAILED      啟動失敗
  ERR,OVERFLOW         原始行過長或 UART 接收丟失

其他錯誤格式：
  ERR,<code>[,<arm>]

有辨識到合法 arm1/arm2 時附手臂；沒有就不附。
LED 回覆會回顯本次設定的 MOVING/STOPPED；沒有位置、馬達 ID、軌跡序號、時間或實體完成欄位。

碼            意義                                  馬達封包
BAD_CMD       不支援的命令                          無
BAD_ARG       欄位／手臂／整數格式、torque 值或 LED 狀態錯誤   無
RANGE         AX 數值可解析但不在 0～1023            無
NO_TARGET     尚無可啟用目標卻要求 torque-on         無
INIT_FAILED   開機初始化失敗，動作鎖住               動作被拒絕；啟動時已嘗試兩臂 off
DXL_TX        本地馬達傳送失敗                      已嘗試，可能部分送出
OVERFLOW      行過長／UART 丟資料                   損壞行不執行

解析順序（用於混合錯誤時的可預測結果）：
1. 原始輸入超長／UART 損壞先 OVERFLOW 丟行。
2. 欄位切割最多八欄；超過八欄先 BAD_ARG。
3. PING/VERSION 只接受一欄；否則 BAD_ARG。
4. LED 驗證手臂、欄位及 MOVING/STOPPED，更新 GPIO 並回覆，不經馬達初始化鎖定。
5. 其餘非 AX/TORQUE 的命令回 BAD_CMD。
6. AX/TORQUE 先驗證手臂，再檢查初始化鎖定。
7. 再檢查該命令欄位、數值與目標資格，最後才傳送。

因此畸形的超多欄舊命令可能先回 BAD_ARG，而不是 BAD_CMD；
所有被拒絕的舊命令都不發封包。初始化鎖定時，有效手臂的動作
優先回 INIT_FAILED，即使其後參數也錯誤。

DXL_TIMEOUT、DXL_RX、DXL_MOTOR、DXL_RANGE、BAD_TRAJ 不再是外部協定錯誤碼。
缺少或錯誤的馬達通常無法靠本版 ACK 偵測，因為沒有單顆回讀。
未知 ERR 也必須停止，不可因客戶端不認識其碼而忽略。


9. ROS 序列轉接實作要求
------------------------------------------------------------

9.1 單一管理者
同一個主機程序／模組獨占序列埠；兩臂控制來源不得各自開埠或直接寫入。
使用一個全域發送佇列，最多一筆 in-flight，包括 PING/VERSION/LED。
只有收到該筆完整精確回覆後，才可發下一筆。

9.2 ACK 核對
- PING 必須為 PONG；VERSION 必須為 VERSION,4。
- AX 必須為 OK,AX,同一手臂。
- TORQUE 必須為 OK,TORQUE,同一手臂,同一 enabled。
- LED 必須為 OK,LED,同一手臂,同一 MOVING/STOPPED，不能只核對前綴。
- 不接受前綴符合、額外欄位、錯臂、錯命令、錯值或殘缺行。
- 無 request ID，因此同臂連續 AX 的 ACK 本身無法識別個別點；
  禁止流水線、超時後補送，以及把舊連線的延遲 ACK 當成新命令回覆。
- 解析空 CR/LF 可略過，但非空未知行必須視為協定異常。
- 每次發送前檢查已到達的接收資料，僅允許空 CR/LF；非空或殘缺舊資料必須中止，不能先送下一筆。
- 回覆接收必須有長度與時間限制；手動終端上限為 256 bytes。
- 檢查後才發生的重啟仍可能與傳送競態，收到後必須中止；本協定不提供跨重啟 exactly-once 保證。

9.3 計算與軌跡
ROS 必須在發送前完成座標到關節的換算及每軸檢查，產生完整四整數。
軌跡 ID、順序與計數只放在 ROS 日誌／內部狀態，不加入序列命令。
ROS 依軌跡時間及上一筆 ACK 安排下一筆發送；若通訊延遲導致落後，
必須由 ROS 決定重規劃或中止，不堆積過期點並一次灌入。
既有馬達速度設定未被 AX 改寫；更新目標間隔不能保證實際運動速度或到位時間。
此介面不是硬即時軌跡控制器，不提供跨兩臂原子同步。

9.4 目標、施力與重連
明確操作流程：AX -> OK -> TORQUE,1 -> OK。
目標可在 torque 關閉时設定；若原本已啟用，AX 可能立即動作。
TORQUE,0 後，下一次啟用前重新成功 AX，不能沿用舊的本地資格假設。
不要求每個 AX 後都重送 TORQUE,1，也不能由橋接層偷偷追加它。
重連／重啟後由 ROS 重新確認機構狀況，不自動恢復舊任務。

9.5 結果與監控
ROS 可記錄送出時間、ACK 時間、手臂、四軸目標、命令結果與異常；
不得把 ACK 包裝為「到位」「抓取成功」或「B 站已釋放」事件。
實際完成判斷須由系統端定義的外部資訊支持。固定等待只能是主機策略，
不能在文件或訊息中宣稱是 CM530 已回報完成。

9.6 停止／保持的能力邊界
本版無 HOLD、當前位置或外部狀態查詢。
若 ROS 要保持當前位置，必須另有可信位置來源與相應策略；
本協定不提供這個來源，也不在此次範圍新增讀取命令。
最後目標不是當前位置，重送最後目標不等於瞬間停止。
停止發送只停止新的目標，已送出的動作可能繼續。
TORQUE,0 為卸力，並非保持姿態或硬體急停；是否使用由上層明確決定。


9.7 LED 通知與終端顯示
ROS 在準備執行動作時送 LED,<arm>,MOVING，等待其 ACK 後再依計畫發送馬達命令。
ROS 依自身的外部完成條件確認停止後，再送 LED,<arm>,STOPPED。
不得以固定等待、最後 AX 的 ACK、TORQUE,0 或 demo 結束替代停止確認。
LED 不新增韌體計算；B 鎖與到位判斷依然在 ROS。

手動終端正常 LED 命令不印 TX -> LED,...，正確 LED ACK 不印 RX <- OK,LED,...，
不增加狀態提示或儀表。這只是顯示策略，序列傳輸與 ACK 核對不能省略。
LED 的 ERR、逾時、錯配 ACK、殘留回覆或重啟仍顯示錯誤並停止本次操作。
其他命令、READY、VERSION 及診斷輸出維持正常。
終端的使用說明與操作者輸入仍可出現 LED 命令文字，並不是移除控制介面。
終端 demo 不自動改燈，手動操作需操作者明確設定。


10. 通訊範例
------------------------------------------------------------

範例全部一問一答。TX/RX 前綴不是線上資料。下面 LED 範例呈現線上契約，正常終端不印該組收發文字。
不同小節為獨立情境；遇錯誤後不表示同一連線可自動續送。

10.1 成功啟動與單臂命令（位置僅為示範）
RX <- READY,4
TX -> VERSION
RX <- VERSION,4
TX -> PING
RX <- PONG
TX -> AX,arm1,512,512,512,512
RX <- OK,AX,arm1
TX -> TORQUE,arm1,1
RX <- OK,TORQUE,arm1,1
TX -> AX,arm1,520,512,512,512
RX <- OK,AX,arm1

10.2 兩臂交錯更新
前提：兩臂已由 ROS 確认適合移動，且各自完成目標設定與明確啟用。
TX -> AX,arm1,520,512,512,512
RX <- OK,AX,arm1
TX -> AX,arm2,510,512,512,512
RX <- OK,AX,arm2
主機依時間及實際完成條件判斷後續時機，不送 BEGIN/PT/END。

10.3 明確卸力
TX -> TORQUE,arm2,0
RX <- OK,TORQUE,arm2,0
這只清除 arm2 資格；arm1 不受影響。重新啟用 arm2 前須成功 AX。

10.4 開機後未設定目標就啟用
TX -> TORQUE,arm1,1
RX <- ERR,NO_TARGET,arm1
主機停止當次流程；經上層明確處理後才開始新的目標設定流程。

10.5 格式／範圍及移除命令（各自獨立範例）
TX -> AX,arm1,512
RX <- ERR,BAD_ARG,arm1

TX -> AX,arm2,1024,512,512,512
RX <- ERR,RANGE,arm2

TX -> AX,arm3,512,512,512,512
RX <- ERR,BAD_ARG

TX -> HOLD,arm1
RX <- ERR,BAD_CMD,arm1

10.6 傳送失敗
TX -> AX,arm1,520,512,512,512
RX <- ERR,DXL_TX,arm1
arm1 目標資格清除。主機停止兩臂佇列；不能斷言這筆完全未送到馬達。

10.7 初始化失敗
RX <- ERR,INIT_FAILED
主機停止啟動，不進入正常動作流程。
診斷者仍可單獨送 VERSION/PING；即使回覆正常，動作鎖定不解除。

10.8 超時／錯配／重啟
送 AX 後兩秒沒有完整 ACK：停止，不自動重送。
送 AX,arm1,... 卻收到 OK,AX,arm2：停止，不把它當成其他佇列項完成。
送 TORQUE,arm1,1 卻收到 OK,TORQUE,arm1,0：停止。
等待任一 ACK 時收到 READY,4：視為重啟，停止；不要自動接續或卸力。
不存在「最後一筆 END 成功因此實體軌跡完成」的流程。


10.9 LED 線上範例（終端正常收發靜默）
TX -> LED,arm1,MOVING
RX <- OK,LED,arm1,MOVING
ROS 可接著傳送計畫中的馬達命令；LED 本身不使馬達動作。
在 ROS 確認停止後：
TX -> LED,arm1,STOPPED
RX <- OK,LED,arm1,STOPPED

TX -> LED,arm2,MOVING
RX <- OK,LED,arm2,MOVING
TX -> LED,arm2,STOPPED
RX <- OK,LED,arm2,STOPPED

錯誤範例（終端仍顯示錯誤，停止後續發送）：
TX -> LED,arm1,0
RX <- ERR,BAD_ARG,arm1
手動終端會先在本地拒絕此非法輸入；以上為直接從序列埠送入的韌體結果。


11. 整合驗收
------------------------------------------------------------

11.1 已實作離線測試的責任
- 兩臂只寫各自四個 ID；目標/torque 寫入地址正確，不發 runtime READ。
- 開機只發兩次 torque-off、資格清除、初始化失敗鎖住動作。
- 無資格不啟用；AX 成功建立資格，傳送失敗清除；TORQUE,0 失敗也清除。
- 另一臂資格不受影響；格式錯誤不送封包、不改資格。
- 舊命令／單值 AX 拒絕；非法整數、範圍、UART 溢位恢復。
- 終端版本與精確 ACK，ERR／超時／重啟後沒有後續動作。
- LED 開機雙紅、紅綠互斥、雙臂獨立、不改馬達資格或發送馬達封包。
- 實際 GPIO 適配層的低電位控制、GPIOB/C 時鐘、POWER/UART 腳位不變。
- 終端 LED 靜默但嚴格核對 ACK；錯誤可見且不再追加命令。
- ARM 建置與 ELF/HEX/BIN 一致性、版本識別、雜湊。
實際執行日期與證據以 VALIDATION.md 為準。

11.2 實機 CM530 驗收（目前待驗證）
1. 燒錄新版，核對 READY,4、VERSION,4、PONG。
2. 觀察開機 torque-off，不自動移至 512、不自動施力。
3. 分臂確認完整目標與 TORQUE,1，小幅移動只影響指定臂。
4. 確認 TORQUE,0 卸力及重新設定目標才能啟用。
5. 交替傳送雙臂 AX，確認一問一答與實體 ID 對應。
6. 受控測試斷線／重啟，不把停止送命令當成已停止運動。
7. 逐燈確認 MANAGE 綠、PROGRAM 紅、TX 綠、RX 紅；開機雙紅、四種 LED 切換皆不動馬達。
8. 確認 LED 不影響序列通訊，正常終端不印 LED 收發但錯誤仍可見。
不得用離線 PASS 代替實機完成。

11.3 ROS 外部整合驗收（本儲存庫未實作）
- 兩臂同時請求 B 站時，只有一方可取得鎖，未實際離開不釋放。
- A/B 視覺事件能驅動正確任務；吸取/放置未確認不進入下一物理步驟。
- C 站 1～4 占用時選 5；更低格空出時依規則選最小可用格。
- 預留或未知格不被重複使用；滿八格才回報排列完成。
- Return 使用校正姿態；CM530 ACK 不直接觸發到位或釋鎖。
- 一筆 ERR／逾時／錯配／重啟會中止兩臂共用發送佇列。
- 序列埠只有一個持有者；手動終端運行時 ROS 不搶占。
- 重連不重送舊軌跡，不自動追加 torque-off 或 torque-on。


12. 版本遷移與能力限制
------------------------------------------------------------

協定 2/3 -> 4 的遷移：
- 從協定 3 升級後新增 LED 指令與開機雙紅，終端正常 LED 收發靜默，馬達直接轉接行為保持。
- READY/VERSION 改為 4，舊客戶端必須一起更新。
- 以下從協定 2 遷移的規則維持：AX 只接受四個位置；由呼叫者明確提供每軸數值。
- HOME 移至 ROS 姿態配置；不能自動展開為固定 512。
- BEGIN/PT/END 移至 ROS 軌跡與排程，線上只送 AX。
- HOLD 移除且沒有等效替代；若需要位置保持，另行設計外部來源與策略。
- STOP 仍不支援；不映射為 HOLD 或 TORQUE,0。
- 移除軌跡／位置回讀錯誤碼及馬達 ID 回覆欄位。
- 開機 torque-off、目標資格、明確 torque 控制與無斷線自動動作維持。

韌體不改馬達 EEPROM，不新增速度控制，不保證即時性、到位、
物品抓取成功或機械停止。這些限制是介面事實，不可在 ROS wrapper 中
包裝成已確認的硬體狀態。

維護時同步更新根 README、第 16 版 README、本規格、終端、測試、
VALIDATION、映像檢查器與 SHA256SUMS。其他歷史資料夾維持原樣。
